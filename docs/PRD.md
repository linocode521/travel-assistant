# PRD：智能旅行助手

> 状态：v1.0 · 2026-11-18 · 负责人：linocode521
> 本文档只描述「要什么、为什么」，不含实现细节（实现见 README）。

---

## 1. 概览

### 问题陈述

想在国内某座城市玩 2~3 天的人，出发前要花一到两小时在攻略站、地图、点评之间来回切换，把景点、路线、时间、预算拼成一份能照着走的计划。[hunch]

拼完还不放心：路线可能绕远、景点之间时间不够、总花费超了预算，其中任何一项出问题都要整份重排。[hunch]

**不解决的代价**：要么在路上现查、浪费游玩时间；要么干脆跟团，放弃自由度。

> 判据：这句话里没有出现任何功能名。「解决」的定义是——用户拿到一份当天可以直接照着走的清单，且在地图上走得通、在时间里塞得下、在预算内花得完。

### 建议方案

用户输入目的地、日期、偏好、节奏、人数、预算，系统产出一份按地理位置排布、带交通耗时、预算逐项拆分的行程，并在地图上可视化成编号路线。用户可以删改任何一项，地图与费用实时跟着变，最后导出成 PDF 或长图带走。

### 成功指标

| 指标 | 当前基线 | 目标 | 类型 |
|---|---|---|---|
| 从「有想法」到「有可执行行程」的耗时 | 60~120 分钟（人工拼攻略）[hunch] | **< 5 分钟** | 结果 |
| 首次生成即无报错率 | 未测量 [un-baselined] | > 95% | 采纳 |
| 行程被直接采用（未做结构性删改）的比例 | 未测量 [un-baselined] | > 60% | 结果 |
| 生成延迟 P50 / P95 | 规则版 0.03s / AI 版 86s [data] | P50 < 1s，P95 < 90s | 采纳 |
| 预算估算偏差 | 未测量 [un-baselined] | 与实付偏差 < 15% | 护栏 |

**护栏说明**：不能为了「跑得快」牺牲行程质量——如果用户拿到快但绕路的行程，指标 1 会变好、真实体验变差。所以指标 5（预算偏差）和「直接采用率」共同构成护栏。

## 2. 背景

### 为什么是现在

- 大模型的常识足够覆盖「某城市有哪些值得去的地方」，但**不擅长空间与时间的约束求解**——这正好是规则引擎的强项，两者互补的组合方案现在才成熟。[hunch]
- 国内地图 API（高德/腾讯）的 POI 数据覆盖到区县级，坐标与图片可直接取用。[data]

### 战略对齐

个人作品集项目。目标是证明「AI 产品不只是聊天壳子」——把大模型放进一个有明确约束、有兜底、有可验证输出的工程体系里。

### 用户研究摘要

**没有做正式用户研究。** 当前所有关于用户行为的判断都来自开发者自身的旅行经验，标记为 [hunch]。这是本文档最大的缺口，见附录。

## 3. 用户故事

### US1 · 生成一份能走的行程

> 作为想周末去某城市玩两天的人，我想输入偏好后直接拿到一份按天排好的行程，这样我不用自己比较景点和查路线。

**验收标准**
- 输入目的地、日期、天数、偏好、节奏、人数即可生成
- 行程按天分组，每天含时间、景点名、停留时长、交通方式与耗时
- 同一天内景点按地理位置聚集，不出现来回横跳
- 生成失败时降级到本地规则，**不出现空白页或报错弹窗**

### US2 · 在地图上看懂路线

> 作为拿到行程的人，我想在地图上一眼看出今天要去哪几个地方、怎么走，这样我能判断这份行程合不合理。

**验收标准**
- 地图上按顺序显示编号标记
- 每天的路线用虚线连接
- 地图加载失败时自动降级到备选方案，不影响文字行程的阅读
- 点击标记能看到景点名

### US3 · 知道要花多少钱

> 作为预算有限的人，我想在出发前知道这趟大概花多少、钱花在哪，这样我能提前调整。

**验收标准**
- 按门票/住宿/餐饮/市内交通分类展示
- 每类可展开到单项（如「故宫 ¥60 × 2 人」）
- 显示总计、人均、日均
- 超出预算上限时明确提示超出多少

### US4 · 改到满意为止

> 作为拿到初版行程的人，我想删掉不感兴趣的、加一个想去的，这样行程才是我自己的。

**验收标准**
- 可删除、上下移动任意条目
- 可锁定条目，重排时不被替换
- 可加天、删天
- **任一改动后，地图与预算立即更新，不需要手动刷新**

### US5 · 带着走

> 作为马上要出发的人，我想把行程存到手机里或打印出来，这样路上不用一直开着网页。

**验收标准**
- 可导出 PDF（适合打印）
- 可导出长图（适合发微信）
- 可导出纯地图图片
- 导出内容与页面所见一致

### US6 · 手机上随手看

> 作为已经在路上的人，我想在地铁上打开手机看一眼下一站去哪，这样不用回酒店开电脑。

**验收标准**
- 微信小程序可打开，页面在 3 秒内可用
- 地图使用设备原生地图组件
- 断网时显示明确的错误提示，不是白屏

### US7 · 任意城市

> 作为想去非热门城市的人，我想输入任何城市都能生成，而不是只有几个选项。

**状态：未实现，见 Open Questions Q1。**

## 5. 设计与体验

### 核心流程

```
填写条件 ──> 生成 ──> 查看行程 ──> 增删调整 ──> 导出
                        │
                        └── 地图 / 预算 实时跟随
```

### 关键设计决策

**D1 · 先秒出，再升级**
AI 生成要 86 秒 [data]，直接让用户等会流失。改为：先返回规则版（0.03s），AI 版回来后覆盖同一条记录。
**代价**：用户可能已经基于规则版开始编辑，AI 版覆盖会丢失这些修改。**缓解**：覆盖前若检测到用户编辑则放弃覆盖（待实现）。

**D2 · 双引擎不是降级，是主路径**
把规则引擎当"兜底"是浪费——它 0.03 秒出结果，本身就适合做第一响应。

**D3 · 地图失败不阻塞文字**
地图是增强，不是必需。加载失败时文字行程完整可读。

### 错误状态

| 场景 | 表现 |
|---|---|
| 后端未启动 | 首页顶部红色提示条，说明原因与解决方式 |
| 大模型超时/无 Key | 自动降级规则版，页面标注「本地规则」 |
| 地图库加载失败 | 切 Leaflet；再失败则显示说明文案，文字行程不受影响 |
| 城市无数据 | 明确提示"该城市暂未收录"，不返回空页面 |

## 6. 技术考虑

### 架构要点

- **前后端分离**：无构建步骤的前端 + Flask JSON API
- **坐标一致性**：POI 原始数据是 WGS-84，地图用 GCJ-02，统一转换，否则景点偏移 300~500 米
- **地图双实现**：高德优先，Leaflet 兜底
- **导出在服务端**：PDF 用 reportlab，地图图片用高德静态图 REST

### 依赖与风险

| 依赖 | 风险 | 缓解 |
|---|---|---|
| DeepSeek API | 超时、限流、Key 失效 | 规则引擎兜底 |
| 高德 JS API | 加载失败、配额耗尽 | Leaflet 降级 |
| 高德图片床 | 图片 404 | 无图不留空位 |
| 国内网络访问 GitHub | 部署时拉代码失败 | 本地打包上传 |

## 7. 实施计划

### Phase 1 · MVP（已完成）

- 6 城 POI 库、双引擎、地图、预算、编辑、导出、小程序版
- **砍掉的原因**：任意城市需要 LLM 提名 + 地图校验的两段式链路，比本地库慢且不稳定，MVP 期先保证"一定能生成"。

### Phase 2 · 待做

- 任意城市支持（LLM 提名 + 地图校验 + 编造过滤）
- AI 生成提速（目标 P95 < 60s）
- 用户研究：找 5 位真实用户走一遍，记录卡点
- **重入口条件**：Phase 1 的「直接采用率」有数据后，判断扩展城市是否值得

### Phase 3 · 远期

- 多人协作、行程分享链接
- 实时预订对接
- 离线包

## 假设与缺口

- **没有任何真实用户研究。** 问题陈述里的「60~120 分钟」和「拼完要重排」都来自开发者自身经验 [hunch]。找 5 个真实用户各走一遍，是当前投入产出比最高的一件事。
- **所有成功指标都缺基线。** 除了生成延迟和仓库密钥扫描有实测数据 [data]，其余四项 `[un-baselined]`——目标值是我拍的，不是推导出来的。没有基线就无法判断上线后是变好还是变坏。
- **目标用户画像未验证。** 假设是「2~3 天的国内短途自由行」，但如果是「5 天以上深度游」，现有的按天分簇算法和 POI 密度都不够用，产品需要重新设计。
- **最可能推翻这份文档的信息**：用户其实不需要「完整行程」——他们可能只想要「今天下午去哪」这种即时决策支持。如果真是这样，整个产品形态要重来。
